# 子任务委派（subagent）规范

> 目的：**最难的「想」交给 Fable，主会话（当前模型）做复核与交互，执行外包给便宜的 subagent**。执行委派的收益有两层：便宜模型单价低；更重要的是**上下文隔离**——测试日志、文件全文、大段 diff 留在 subagent 内，不进入主会话，后续每一轮都不再为它们付费，也不会把主会话推向压缩（开发中途触发压缩会让已确认的方案被摘要化，这是真正的质量损失）。

## 分工原则

| 层 | 谁做 | 内容 |
|----|------|------|
| 思考 | `planner`（Fable） | 实现方案设计、bug 根因 + 修复方案、小 PR 审查（见「思考委派」） |
| 决策 | 主会话 | 需求理解、复核方案、跨文件一致性、与用户的闸门交互、验收复核 |
| 执行 | subagent | 定位、跑测试、按实施单改代码、模板化成文、压缩 diff |

主会话**不亲自做**吞吐型工作，但**必须亲自做**最终判断：subagent 的结论是输入，不是结果。

## 何时委派

满足任一即委派；否则直接在主会话做（委派本身有开销：写任务说明 + 结果回传）：

| 条件 | 典型步骤 |
|------|---------|
| 步骤会往主会话灌入大量原始输出（估计 > 1 万 token） | 跑测试、拉大 diff、批量 grep |
| 步骤可按单元切分且各单元相互独立 | 逐单元实施、多模块搜索 |
| 步骤不依赖主会话已积累的上下文 | 一条命令 + 判定规则即可完成 |

**不委派**：与用户交互的闸门、最终验收、执行中途的跨层契约变更。方案设计走 `planner`，素材由主会话内联。

**豁免要收窄**：命令里写了「范围很小时可直接做」的豁免，只在**确实已知**范围时适用（用户点名了文件、或改动确定落在 ≤3 个文件内）。「我觉得应该不大」不算已知——不确定就委派。跳过委派时在过程中说明一句理由。

## 可用 agent（随插件分发，位于 `plugins/rd/agents/`）

**只读型**（不改任何文件）：

| agent | 模型 | 用途 | 返回 |
|-------|------|------|------|
| `code-scout` | 会话模型 · high | 按关键词定位相关代码（实现处/调用链/同类参照） | 文件清单（路径、相关度、关键行、原因），不含文件内容 |
| `test-runner` | 会话模型 · medium | 执行给定测试命令 | 计数 + 失败用例（file:line、断言、精简堆栈） |
| `diff-digest` | 会话模型 · medium | 拉取并压缩大 diff，可逐文件落盘 | 按文件的改动类型/行数/涉及符号 + 结构性改动清单 |
| `planner` | fable | 出实现方案 / 根因 + 修复方案 / 小 PR 审查意见 | 按调用方骨架填好的结论 + 存疑项 |

**可写型**（会改文件，准入条件见下节）：

| agent | 模型 | 用途 | 返回 |
|-------|------|------|------|
| `impl-worker` | 会话模型 · high | 按实施单修改一个独立单元的代码 | 改动摘要 + 验收结果 + 越界需求/存疑项 |
| `doc-writer` | 会话模型 · medium | 按素材和模板骨架成文/回填章节 | 产物路径 + 要点核对表 |
| `ui-verifier` | 会话模型 · medium | 把一条 UI 验证项写成 headless Playwright 探针并运行，截图只在 agent 内判读 | 每项 PASS/FAIL/BLOCKED + 一句证据 + 探针/产物路径 |

命令的 frontmatter `allowed-tools` **必须包含 `Agent`**（`allowed-tools` 是免确认预授权而非白名单：缺失时仍能派生，但每次派生都弹确认，打断流程）。

代码质量审查不在此列：`/rd:review` 大 PR 直接调原生 `/code-review`（Skill 工具，`allowed-tools` 需列 `Skill`），规则见该命令。

## 思考委派（planner）

命令不写 `model`，全程跑当前会话模型；只把「想」的一步交给 `planner`（`model: fable`）。这样 Fable 不可用时能降级：钉在命令上的 Fable 在额度用尽时直接报错，`fallbackModel` 也不处理计费 / 限流错误，只有子代理失败会把错误交回主会话。

1. **素材内联**：任务类型、需求要点或问题描述、分层与规范摘要、`code-scout` 的 file:line 清单、返回骨架，都写进 prompt。planner 自己读代码核实，但不负责找需求文档。
2. **主会话复核**：对照功能清单 / 分层 / 根因依据检查返回结论，缺项直接修正或 SendMessage 让它补；「存疑」项带给用户。复核之后再展示给用户确认。
3. **失败降级**：Agent 返回 API 错误（Fable 额度用尽、未开通、云厂商未上架）或超轮仍无结论 → 不重试，主会话用当前模型按同一骨架自己做，产物首行注明 `⚠️ Fable 不可用，…由当前模型生成`。
4. **只委派想，不委派做**：确认后的实施、文档回写、提交都在主会话（或按准入条件派 `impl-worker`）。

diag 插件同理，根因判断交给 diag 自带的 `root-cause` agent（fable），见 `/diag:diagnose` 第 7 步。

## 委派实施（impl-worker）的准入条件

把写代码交出去只在方案已经确定到「机械执行」的程度时才成立。**四条全部满足**才派，缺一条就主会话自己写：

1. **方案已确认**且细到文件级：改哪个文件、哪个函数、改成什么、为什么。用户已经点头。
2. **单元互不依赖**：各单元不改同一个文件，不依赖彼此的中间产物，不共享待定的类型/接口定义。
3. **契约已定**：接口签名、DTO 字段、表结构、错误码在派发前就定死并写进实施单。需要 subagent 去"设计"的部分为零。
4. **有验收手段**：构建命令或测试命令，能判定这一单元做没做对。

**永远不派**：新建抽象或分层、跨层契约变更、需要与用户来回确认的改动、方案本身还在演化的首版实现。

**并行安全**：同一文件只能出现在一个单元里。做不到互斥就串行派，或合并成一个单元。

**`ui-verifier` 不套用这四条**：它写的是验收探针（测试产物，不是产品代码），准入按 `_verify.md`「自主验收」的前置三条。

**验收是主会话的活**：复核 `git diff` 实际内容，不是复核 subagent 的自述。这会把 diff 拉回主上下文——改动大时先用 `diff-digest` 压一遍再看。任何 `越界需求` / `存疑` 条目都由主会话决策，不得让 subagent 自行扩权。

## 委派时必须做到

1. **任务说明自包含**：subagent 没有主会话历史。工作目录、命令、判定规则、项目规范中相关的几条（不是整份文件）都要写进 prompt。
2. **素材内联，不给路径**：要审的 diff、要填的骨架、要照做的实施单，**正文直接写进 prompt**。只给磁盘路径 = 让 subagent 自己去找，它会用掉大半轮次做探索，然后撞上轮次上限交出半成品。素材确实过大（如整份 PR diff）时才落盘，且必须同时在 prompt 里内联**本单元那一份**。
3. **只要结论，不要原文**：agent 定义已规定返回格式；prompt 中再明确「不要回传完整日志/文件内容/diff」。
4. **单元要小**：一个 subagent 一个单元（实施 = 一组必须同时改的紧耦合文件）。宁可多派几个，不要把四五个文件塞进一个——那是撞轮次上限最常见的原因。
5. **独立单元并行**：同一批 subagent 在一次调用里一起发出，结果由主会话汇总、去重、合并跨单元问题。
6. **失败要透传**：subagent 报 ERROR/超时时把原因带回，主会话决定重试或降级为内联执行，不静默吞掉。

## 超轮与失败处理

subagent 报告 `stopped at its N-turn limit` 时，返回的是**部分结果**：

1. **续问，不重派**：用 SendMessage 让它从停下的地方接着输出已核实的结论（重派会丢掉它已经做完的工作，还要再烧一遍轮次）。
2. **记账**：主会话在汇总时标注哪几个单元是部分结果，别当成"审完了/改完了"。
3. **同一批里超轮的超过一半** = 单元切太粗或素材没内联。当轮先续问拿到结果，然后按第 2、4 条纠正切分方式，不要原样再派一遍。

## 与仓库角色 / 调用形态的关系

- 与 `requirementRole` 无关：委派不涉及需求文档写入的角色判定，`doc-writer` 写文档前由主会话按角色决定派不派。
- skill 形态同样适用：Agent 工具随会话可用；agent 定义随 rd 插件安装。
