# 需求评审

提交需求评审（AI 先预审）或记录人工评审结果。代码审查不在这里：审 PR 用 `/rd:review`。

> **Audience:** Product Manager
> 存储路径规则见 [_storage.md](../shared/_storage.md)
> 仅对 REQ 生效；QUICK 没有评审站，草稿即可 `/rd:dev`。
> `readonly` 仓库：预审意见只展示，不写评审记录、不改状态（写操作规则同 `_storage.md`）。

## 命令格式

```
/rd:req-review [REQ-XXX] [pass|reject] [--comment=评审意见]
```

- 省略编号时自动选择「草稿」「评审驳回」或「待评审」的需求
- 多个候选时让用户选择

## 场景一：提交评审（草稿/评审驳回 → 待评审）

当需求状态为「草稿」或「评审驳回」时：

### 1. 完整性检查

检查必填章节是否完整（十一章「实现方案」在 `/rd:dev` 阶段填充，不在此检查）：

```
需求完整性检查

✅ 需求描述 - 已填写
✅ 功能清单 - 3 个功能点
✅ 业务规则 - 5 条规则
✅ 使用场景 - 2 个场景
✅ 接口需求 - 3 个接口能力
✅ 测试要点 - 8 个测试点

检查结果：✅ 通过
```

如果有缺失：
```
❌ 需求完整性检查失败

缺失内容：
- ❌ 业务规则 - 未填写
- ❌ 测试要点 - 未填写

请先完善需求文档：/rd:edit REQ-XXX
```

### 2. AI 预审

读需求全文，再读 `active/` 与 `completed/` 下其它需求的标题、功能清单与范围（只读这几节，不读全文；QUICK 文档没有这两节，只取标题与「问题描述」），从四个维度给意见：

| 维度 | 看什么 |
|------|-------|
| 合理性 | 目标与功能清单是否对得上；业务规则是否自相矛盾；接口需求是否覆盖了功能清单 |
| 粒度 | 功能点是否过多、涉及模块是否过散、是否该先 `/rd:split` |
| 冲突 | 与进行中 / 已完成需求是否重叠、是否改动同一规则而未提及 |
| 风险与遗漏 | 使用场景缺异常流程、测试要点没覆盖业务规则、假设 / 依赖未列 |

意见分三级：**阻塞**（不改就不该进评审）、**建议**（评审人酌情）、**信息**。每条给出章节定位。

输出后：
- 有阻塞项 → 询问「预审有 N 项阻塞，仍要提审吗？(y/n)」。n → 保持当前状态，提示 `/rd:edit REQ-XXX`，退出；y → 继续
- 无阻塞项 → 直接继续

无论是否提审成功，都在「八、评审记录」追加一行：日期、评审人 `AI 预审`、结论（继续提审写 `提审`，用户选 n 写 `预审未提审`）、意见为精简摘要（≤ 200 字，阻塞项优先，无问题写「无阻塞项」）。表里只有占位行 `| - | - | - | - |` 时用首条记录替换它（只动本表，其它章节的同形占位行不碰）。

> 预审只产出意见，不改一~六章的任何内容与结构（Memory 隔离约束同 `requirement-analyzer`）。

### 3. 生成评审摘要

```markdown
## 需求评审摘要

### 基本信息
- 编号：REQ-001
- 标题：部门渠道关联
- 优先级：P1
- 功能点数：6

### 需求概述
在组织部门管理中，实现部门和分组与渠道的关联功能...

### 影响范围
- 模块：sys（系统）、oms（订单）、dashboard（看板）
- 涉及需求：与 REQ-003 共用权限规则

### 风险评估
- 中等风险：涉及权限控制逻辑变更

### AI 预审
- 阻塞 0 · 建议 2 · 信息 1（详见评审记录）
```

带阻塞项仍提审时，本节改为 `- ⚠️ 带 N 项阻塞提审 · 建议 n · 信息 n`，并在下方结尾提示第一行同样标出。

### 4. 更新状态

- 修改元信息状态为「待评审」
- 勾选生命周期「待评审」

### 5. 提示

```
✅ 需求已提交评审（⚠️ 带 1 项阻塞，见评审记录）   ← 无阻塞时不带括号

REQ-001 部门渠道关联
状态：待评审

评审通过后执行：/rd:req-review REQ-001 pass
评审驳回执行：/rd:req-review REQ-001 reject
```

## 场景二：评审通过（待评审 → 评审通过）

当参数包含 `pass` 时：

### 1. 状态检查

```
if 状态 != "待评审":
    错误：当前状态不是「待评审」，无法执行评审操作
    退出
```

### 2. 收集评审信息

```
评审人：<git config user.name 的值>（如需修改请输入）
评审意见：（可选）
```

- **评审人**（必填）：默认取 `git config user.name`，展示给用户确认，用户可修改
- **评审意见**：可选；`--comment=` 给出时直接采用

### 3. 记录评审结果

- 「评审记录」章节追加一行（不覆盖「AI 预审」行）
- 修改元信息状态为「评审通过」
- 勾选生命周期「评审通过」

### 4. 提示

```
✅ 评审通过

REQ-001 部门渠道关联
状态：✅ 评审通过

开始开发：/rd:dev REQ-001
```

## 场景三：评审驳回（待评审 → 评审驳回）

当参数包含 `reject` 时：

### 1. 收集评审信息

```
评审人：<git config user.name 的值>（如需修改请输入）
驳回原因（必填）：
```

- **评审人**（必填）：默认取 `git config user.name`，展示给用户确认，用户可修改
- **驳回原因**（必填）：`--comment=` 给出时直接采用，否则必须输入

### 2. 记录评审结果

- 「评审记录」章节追加一行（驳回原因必填）
- 修改元信息状态为「评审驳回」

### 3. 提示

```
❌ 评审驳回

REQ-001 部门渠道关联
状态：❌ 评审驳回

驳回原因：接口需求需要补充异常场景说明

修改需求：/rd:edit REQ-001
重新提审：/rd:req-review REQ-001
```

## 状态流转图

```
草稿 ────提审────▶ 待评审 ──pass──▶ 评审通过 ──▶ /rd:dev
                     │  ▲
                 reject │ 重新提审（/rd:edit 后）
                     ▼  │
                   评审驳回
```

驳回后状态停在「评审驳回」，不回草稿；修改后再提审直接进「待评审」。
