# 快速修复需求

> **Audience:** Engineer

用于小bug修复或小功能开发，简化流程：无评审，方案确认后即可 `/rd:dev`。

## 命令格式

```
/rd:new-quick [标题]
```

---

## 简化生命周期

```
草稿 → 开发中 → 测试中 → 已完成
```

（只跳过评审；状态机定义见 `_storage.md`「双轨状态机」）

---

## 执行流程

### 0. 解析存储路径

读取 `.devflow/settings.json` 的 `requirementRole` / `requirementsDir`（`.devflow/settings.local.json` 同名字段覆盖）。`readonly` 仓库不能创建需求，提示到主仓执行后终止；否则需求根目录为本仓 `requirementsDir`（缺省 `docs/requirements`），确保其 `active/`、`completed/` 存在。下文 `docs/requirements/` 均指该目录。

### 1. 生成需求编号

格式：`QUICK-XXX`（三位数字，如 QUICK-001）

扫描 `active/` 与 `completed/` 中所有 QUICK-XXX 文件，取最大编号加 1 生成新编号。

### 1.5 （可选）从 issue 导入

若命令带 `--from-issue=#N`，按 [_issue.md 的 Issue 拉取规范](../shared/_issue.md#issue-拉取规范) 拉取 issue：
- issue 标题作为默认标题
- issue 正文作为「问题/需求描述」的初始输入
- 元信息 `issue` 字段填 `#N`（否则填 `-`）

`repoType` 为 `other` 或未配置时提示并退出。

### 2. 收集基本信息

如果未提供标题，询问用户：

**需要收集的信息：**
- 问题/需求描述（必填）
- 类型：bug修复 / 小功能 / 优化（默认：bug修复）
- 优先级（P1/P2/P3，默认 P2）
- **模块**：自动设为「快速修复」（无需用户选择）

### 3. 读取模板

**必须先读取快速修复模板**，确定文档结构：

```
优先级：
1. 本地模板：docs/requirements/templates/quick-template.md
2. 插件模板：${CLAUDE_PLUGIN_ROOT}/templates/quick-template.md
```

**两个路径都不存在时，终止操作**：
```
❌ 未找到快速修复模板文件

请执行 /rd:update-template quick 恢复模板
```

读取后解析模板的完整章节结构，后续创建文档**必须严格保留模板中的所有章节、层级和格式**。

### 4. 创建简化文档

**步骤 4.1：严格按模板结构创建**

使用快速需求模板创建文件：`$LOCAL_ACTIVE/QUICK-XXX-标题.md`

**格式约束（强制）：**
- 章节标题、层级必须与模板完全一致
- 不得新增、删除、合并或重命名模板中的章节
- 未填写的章节保留模板中的占位文本，不得删除
- 表格结构（列名、列数）必须与模板一致

**初始化内容：**
- 填充元信息（编号、标题、类型、状态=草稿、日期）
- **模块字段设为「快速修复」**
- `issue` 字段：从 issue 导入时填 `#N`，否则填 `-`
- 生命周期勾选「草稿」

### 5. 快速分析并生成方案

AI 分析问题/需求，生成实现方案：

#### 5.1 问题分析（如果是bug）
- 分析错误信息/现象
- 定位问题根因
- 确定影响范围

#### 5.2 代码定位
- 搜索相关代码
- 确定涉及的文件
- 理解现有实现

#### 5.3 生成实现方案
- 具体的改动说明
- 涉及文件清单
- 预估改动量（小/中）

### 6. 方案确认检查

在确认前检查：
- [ ] 不命中任何「需要他人点头」信号（新 API、表结构、跨模块、下游可感知、破坏性变更、权限 / 安全 / 资金）——判定表见 [`_granularity.md`](../shared/_granularity.md)
- [ ] 可快速验证

**如果任一不满足**，建议用户升级为正式需求：

```
⚠️ 此改动可能超出快速修复范围：
- 需要新增 API
- 需要修改数据库表结构

建议使用正式需求流程：/rd:new [标题]

```

用户选择改走 `/rd:new` 时，删除步骤 4 刚创建的草稿文件（编号回收，不留孤儿文档）；选择继续则进入步骤 7。

### 7. 方案确认

显示方案摘要，等待用户确认：

```
快速需求：QUICK-001 修复xxx问题

类型：bug修复
优先级：P2

问题分析：
  [问题根因分析]

实现方案：
  [具体实现方案]

涉及文件：
  - internal/xxx/biz/xxx.go（修改）
  - internal/xxx/store/xxx.go（修改）

改动量：小（约 20 行）

```

### 8. 确认后

用户确认后：

1. 将步骤 5 生成的问题分析、解决方案、涉及文件、改动量、验证方式写入文档对应章节（严格保留模板结构，占位文本替换为实际内容）
2. 状态保持「草稿」，在「开发记录」追加一行「方案经用户确认」——方案确认不是独立状态，见 `_storage.md`「双轨状态机」
3. 输出下一步：

```
✅ 方案已确认

QUICK-001 修复xxx问题
文档：docs/requirements/active/QUICK-001-修复xxx问题.md

下一步：
- /rd:dev QUICK-001 - 切分支、开始开发
- /rd:edit QUICK-001 - 调整方案
```

后续与正式需求走同一组命令：`/rd:dev` → `/rd:test` → `/rd:done`，只是没有评审站。本命令不切分支、不改代码、不归档。

## 适用场景

### 适合快速修复的情况

- 简单的 bug 修复（逻辑错误、空指针等）
- 小功能增强（新增字段、调整参数等）
- 代码优化（性能优化、代码整理等）
- UI 微调（文案修改、样式调整等）

### 不适合快速修复的情况

建议使用 `/rd:new` 创建正式需求：

- 涉及数据库表结构变更
- 涉及多个模块的联动修改
- 需要新增 API 接口
- 影响核心业务流程
- 需要多人协作或评审

## 与正式需求的区别

| 对比项 | 快速修复 (QUICK) | 正式需求 (REQ) |
|-------|-----------------|---------------|
| 编号格式 | QUICK-XXX | REQ-XXX |
| 生命周期 | 4 阶段（草稿 → 开发中 → 测试中 → 已完成） | 6 阶段 |
| 评审环节 | 无 | 有 |
| 测试环节 | `/rd:test` 按「验证方式」验证 | `/rd:test` 按「测试要点」验证 |
| 文档详细度 | 简化 | 完整 |
| 适用场景 | 小改动 | 中大型需求 |

选型判定见 [`_granularity.md`](../shared/_granularity.md)「REQ / QUICK / 无文档的选择」。
