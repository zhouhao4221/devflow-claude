## 一、需求描述

### 1.1 背景

DevFlow 的每个能力同时以两种形态分发：

- **`commands/<name>.md`** —— 面向标准 Claude Code（CLI/桌面/IDE），支持 slash 调用、`model` 分级、`allowed-tools`、共享子文件（`_storage.md` 等）。
- **`skills/<name>/SKILL.md`** —— 面向**不支持 slash command 的 Claude 客户端**（纯 Claude 生态，不涉及非 Claude 的 AI 工具），通过技能语义调用。这是 skill 形态存在的根本理由，**不可删除**。

两份是 v2.36.0（PR #62）一次性批量转换生成的，之后**纯手工维护，没有任何同步机制**（已核查：无同步命令、无脚本、无 CI）。由此产生两类缺陷：

1. **内容漂移**：改了 command 容易忘改 skill。实测 `req:commit` 的 command（309 行）与 skill（307 行）已不一致。
2. **内容残缺**：66 个镜像 skill 中有 **25 个**只在正文写"详见 `_storage.md`"之类指针，但子文件内容**未内联**。skill 是单文件分发、子文件不随之分发，导致不支持 slash 的 Claude 客户端读到的是残缺指令（存储路径、issue 关闭逻辑、Gitea 平台差异等关键约束全部丢失）。

> 25 个残缺 skill 按缺失子文件分布：`_issue.md`（10）`do/new/commit/done/fix/new-quick/dev/specs/issue` · `_storage.md`（8）`prd/migrate/use/review/prd-edit/specs/update-template/release` · `_common.md`（6）api 的 `gen/search/map/import`、pm 的 `stats/pm` · `_granularity.md`（2）`edit/split` · `_gitea_cli.md`（1）`release`。

### 1.2 目标

- **功能目标**：建立确定性的单源派生机制——`commands/*.md` 为唯一权威源，`skills/*/SKILL.md` 由脚本自动生成（含子文件内联）。维护者只改 command，skill 自动重生成。
- **效果目标**：两份永不漂移、永不残缺；新增命令零额外手工；不支持 slash 的 Claude 客户端获得与 command 等价、内容完整的能力。

### 1.3 客户场景

- **场景1**：维护者修改 `commands/commit.md` 或其引用的 `_issue.md`，运行生成器后 `skills/commit/SKILL.md` 自动同步，提交时两份天然一致。
- **场景2**：发布前在 `/req:release` 中执行 `--check`，自动发现任何 skill 与 command 的不一致并重新生成。
- **场景3**：不支持 slash 的 Claude 客户端用户调用某技能，得到完整内联了存储/CLI/业务约束的指令，功能不再残缺。

### 1.4 价值

- **消除漂移**：用确定性脚本替代手工维护，根除两份不一致的隐患。
- **补全残缺**：一次性修复 25 个内容不完整的 skill。
- **降低维护成本**：维护者只维护一处（command），skill 自动派生。

### 1.5 范围与边界

- **本期包含**：
  - 确定性生成脚本（frontmatter 降级 + 子文件内联 + helper 跳过 + `--check` 校验）
  - 全量重新生成 66 个镜像 skill
  - 接入发布流程（`/req:release` 前置步骤或独立命令）
  - CLAUDE.md 规范更新（声明单源派生、禁止手改 SKILL.md）
- **不包含**：
  - 删除 skill 形态（兼容需求真实存在，必须保留）
  - 改造 14 个手写 helper skill（生成器跳过、不触碰）
  - 为 skill 形态补 `model` 分级（目标 Claude 客户端不支持 frontmatter，固有限制）

### 1.6 干系人

- **DevFlow 维护者**：日常只编辑 command，发布前运行生成器。
- **下游用户（标准 Claude Code）**：使用 command，体验不变。
- **下游用户（不支持 slash 的 Claude 客户端）**：使用 skill，获得完整能力。

## 三、业务规则

### 3.1 派生规则（command → skill）

| 输入（command） | 输出（skill） |
|---|---|
| frontmatter `description` | 保留为 skill `description` |
| frontmatter `name`（或文件名） | 作为 skill `name` |
| frontmatter `argument-hint`/`allowed-tools`/`model` | 删除 |
| 正文 `[文案](./_storage.md)` 或 `` 详见 `_storage.md` `` | 替换为 `_storage.md` 完整内容 |
| 正文其余内容 | 原样保留 |

### 3.2 内联规则

- 内联范围：`commands/` 下的 `_*.md` 与 `*-rationale.md`。
- 同一子文件被多命令引用时，各自内联各自副本（skill 间隔离，是兼容性的体积代价）。
- 嵌套引用需递归展开，或在约定中明确不允许嵌套。

### 3.3 体积取舍

内联后个别 skill（如 `release`）将超 30KB token 阈值。该阈值面向标准 Claude Code 的 token/cache；skill 运行于不支持 slash 的 Claude 客户端，**功能完整性优先于体积**，全量内联，不为压缩牺牲完整性。

### 3.4 边界规则

- 生成器只写有同名 command 的 `skills/<name>/`，绝不触碰 helper skill。
- 幂等：同一 command 多次生成产出字节级一致的 skill。

## 四、使用场景

### 场景1：日常维护某命令

维护者编辑 `commands/commit.md` → 运行生成器 → `skills/commit/SKILL.md` 自动重写并内联最新 `_issue.md` → 提交时两份一致。

### 场景2：发布前校验

`/req:release` 执行生成（或 `--check` 比对）→ 发现不一致则重新生成并纳入本次发布。

### 场景3：新增命令

维护者只新建 `commands/foo.md` → 生成器自动产出 `skills/foo/SKILL.md`，无需手写第二份。

## 五、数据与交互

本需求为工具链机制，无终端用户数据，处理对象为**文件**：

- **输入数据**：`plugins/<plugin>/commands/*.md`（排除 `_*.md`）+ 被引用的 `_*.md` / `*-rationale.md`。
- **输出数据**：`plugins/<plugin>/skills/<name>/SKILL.md`。
- **跳过集合**：`skills/` 下无同名 command 的目录（helper skill）。
- **交互方式**：命令行调用生成脚本；`--check` 模式输出人类可读的生成/更新/跳过/超阈值清单；退出码区分「已同步」「有漂移」「出错」。

## 六、测试要点

### 6.1 技术测试

- 全量生成后逐个镜像 skill 校验：① frontmatter 仅含 `name`+`description`；② 无残留子文件指针；③ 无悬空相对链接。
- 25 个原残缺 skill 内联后，子文件关键约束确实出现在正文。
- 14 个 helper skill 生成前后**字节不变**。
- 幂等性：连续运行两次，第二次无文件变更。
- `--check` 在故意改坏一个 skill 后能正确报漂移。

### 6.2 验收标准

- 维护者只改 command 即可，无需手动维护 skill。
- `req:commit` 等已漂移文件恢复一致。
- 抽样核对 `commit`（引用 `_issue.md`）、`release`（引用多个大子文件）产出可读、完整。
- 生成步骤纳入发布流程，CLAUDE.md 明确「禁止手改 SKILL.md」。

## 十、关联信息

- **关联需求**：无。
- **起因**：v2.36.0 / PR #62「将所有 command 迁移为 skill」一次性转换后缺少持续同步机制。
- **外部依赖**：Python3（生成脚本，无第三方依赖，与 `swagger-parser.py` 风格一致）。
- **假设**：command→skill 为确定性机械变换，可脚本化。
- **风险**：内联使个别 skill 超体积阈值（已在 3.3 接受）；嵌套子文件引用需递归处理（11.4 覆盖）。
- **相关文档**：`docs/design/token-optimization.md`、`CLAUDE.md`「命令与技能结构」、`docs/changelogs/2.36.0.md`。

## 十一、实现方案

> 初步技术方案，dev 阶段 AI 分析代码后细化。

### 11.1 数据模型

无持久化数据。处理对象为文件（输入/输出/跳过集合见「五、数据与交互」）。

### 11.2 脚本设计

`scripts/gen-skills.py`（Python3，无第三方依赖，建议置于仓库根 `scripts/`，因跨 5 个插件）：

```
gen-skills.py [--check] [--plugin <name>] [--command <name>]
  默认：全量生成，写入 skills/
  --check：只比对，报漂移/残缺，不写文件，非零退出码表示有差异
```

转换流程：解析 frontmatter（YAML 块）→ 重建为 `name`+`description` → 正文识别子文件引用（链接式 `(./_x.md)` 与纯文本式 `` `_x.md` ``）→ 读 `commands/_x.md` 内联（递归校验无嵌套）→ 写出。

### 11.3 文件改动清单

- 新增：`scripts/gen-skills.py`。
- 重写：66 个 `skills/<name>/SKILL.md`（脚本统一产出）。
- 修改：`plugins/req/commands/release.md`（+ 同步镜像）增加生成/校验步骤，或新增独立命令文件。
- 修改：`CLAUDE.md`「命令与技能结构」「维护规则」声明单源派生、禁止手改 SKILL.md，并修正此前误述的「`/req:update` 同步两者」。
- 丢弃：当前工作区针对镜像 skill 的手工改动。

### 11.4 实现步骤

1. 编写 `gen-skills.py`，实现 frontmatter 降级 + 子文件内联（含嵌套递归）+ helper 跳过 + `--check`。
2. 在 `commit`、`release` 两个命令上验证产出（人工核对内联完整、可读）。
3. 全量生成 66 个 skill，diff 复核。
4. 接入 `/req:release`（或独立命令）。
5. 更新 CLAUDE.md，加入 CI/发布前 `--check` 约束。
