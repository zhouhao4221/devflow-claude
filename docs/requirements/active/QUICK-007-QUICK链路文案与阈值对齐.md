## 问题描述

### 现象

**A. 粒度阈值四处不一致，且判断轴选错**

| 出处 | 说法 |
|------|------|
| `_granularity.md:77` | 重构/优化超过 5 个文件 → 用 REQ |
| `do.md:67-68` | 改动 5~15 个文件 → 建议 QUICK |
| `split.md:54` | 少于 5 个文件 → 可能太小，考虑 QUICK |
| `new-quick.md:145` | 改动范围可控，建议 < 5 个文件 |

同一个 8 文件的重构，`do` 建议建 QUICK，`_granularity` 要求建 REQ，用户会直接撞上。更根本的问题是四处都拿「文件数」当分界线：5 个文件的表结构变更和 15 个文件的批量改措辞风险完全不同，文件数是最容易漂移、也最不靠谱的信号。

**B. `upgrade.md` 元信息转换表自相矛盾**（`upgrade.md:56-58`）

「改动类型 → 类型（bug修复→后端）」与「端类型 → 类型（直接映射）」两行同时写 REQ 的「类型」字段，前者会把一个前端 bug 修复标成后端。

### 期望

REQ / QUICK / 无文档三层的选择标准只在 `_granularity.md` 定义一次，判断轴改为「是否需要留痕」「决定是否需要他人点头」两问，文件数只做兜底提示；`do.md`、`split.md` 改为引用，不各写一份数字。`upgrade` 的类型字段只由端类型映射。

## 实现方案

### 问题分析

阈值是 `do` / `split` 各自补充建议时写偏的，没有回到 `_granularity.md` 对齐；`upgrade.md` 的转换表写于 QUICK 引入初期，后来加「端类型」字段时没删旧行。均为文档措辞问题，不涉及流程逻辑，因此不走正式需求。

`new-quick.md` 同样引用了阈值，但该文件由 REQ-006 整体重写（缩为只创建），其阈值引用随 REQ-006 一并改，本需求不碰它，两者无共同文件。

### 解决方案

1. **`plugins/rd/shared/_granularity.md`「REQ 与 QUICK 的选择」**改写为三层判定表，确立为唯一权威：

   | 需要留痕？ | 决定需要他人点头？ | 用 |
   |---|---|---|
   | 否 | 否 | `/rd:fix` / `/rd:do` |
   | 是 | 否 | QUICK |
   | 是 | 是 | REQ |

   「需要他人点头」的信号：新 API、表结构变更、跨模块联动、影响下游用户、破坏性变更——命中任一即 REQ，与文件数无关。文件数只保留一句兜底：「超过 15 个文件时先考虑拆分」（沿用同文件「拆分建议」既有阈值）。
2. **`plugins/rd/commands/do.md`**：规模判定表的「中等 5~15 个文件 → 建议 QUICK」改为按上表判定，删除数字；保留「轻量 → 直接执行」的语义但判据改为「无需留痕」。
3. **`plugins/rd/commands/split.md`**：3.4「REQ vs QUICK 判断」与「< 5 个文件可能太小」改为引用 `_granularity.md` 判定表。
4. **`plugins/rd/commands/upgrade.md`** 4.1 元信息转换表：删除「改动类型 → 类型」一行，类型只由「端类型」映射；改动类型并入「关联需求」说明（如「升级自 QUICK-XXX（bug修复）」）。

### 涉及文件
